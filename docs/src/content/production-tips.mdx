## Pre-warming the Hash Table

FyroDB starts with minimal shard tables (8 slots per shard) to keep idle memory at ~5 MB. When you first load 1M+ keys, the tables grow dynamically through several doublings (8→16→32→...→32768). Each growth pauses that shard briefly.

To avoid growth pauses during peak traffic, pre-warm the server after startup:

```bash
# Pre-warm with dummy keys, then delete them
redis-cli -p 8000 DEBUG POPULATE 100000
redis-cli -p 8000 FLUSHALL
```

Or insert your expected key count at deployment time before routing traffic. After pre-warming, Pipeline-64 SET throughput improves from ~9M to ~17M ops/sec.

## Recommended Configuration

### High-Throughput (dedicated server, 8+ cores)

```bash
FYRODB_WORKERS=0          # auto-detect CPU cores
FYRODB_SHARDS=0           # auto (workers × 4)
FYRODB_MAX_KEYS=10000000  # 10M keys
FYRODB_MAX_CLIENTS=50000
```

### Memory-Constrained (Docker, 512MB limit)

```bash
FYRODB_WORKERS=2
FYRODB_SHARDS=8
FYRODB_MAX_KEYS=1000000
FYRODB_MAX_CLIENTS=5000
```

### Low-Latency (small dataset, fast responses)

```bash
FYRODB_WORKERS=4
FYRODB_SHARDS=16
FYRODB_MAX_KEYS=100000
```

## Docker Best Practices

```yaml
services:
  fyrodb:
    image: rana718/fyrodb:latest
    ports:
      - "8000:8000"
    environment:
      - FYRODB_WORKERS=0
      - FYRODB_MAX_KEYS=5000000
      - FYRODB_RDB_PATH=/data/fyrodb.rdb
      - MIMALLOC_PURGE_DELAY=0
    volumes:
      - fyrodb-data:/data
    deploy:
      resources:
        limits:
          memory: 2G
```

Setting `MIMALLOC_PURGE_DELAY=0` ensures freed memory is returned to the OS immediately, keeping container RSS accurate.

## Memory Behavior

FyroDB uses mimalloc which eagerly decommits unused pages. After bulk deletes or FLUSHALL:

- RSS drops within 10 seconds (periodic `mi_collect`)
- FLUSHALL triggers immediate collection + purge
- No manual MEMORY PURGE needed (unlike Redis with jemalloc)

If you store 1M keys and then delete them, RSS returns close to the ~5 MB
baseline within 10-20 seconds automatically.

### What does not come back

A mixed workload leaves some memory resident that a pure string workload does
not. After the full benchmark suite plus `FLUSHALL`, a node reports
`used_memory: 0.58 MB` against ~50 MB resident — almost nothing is live, and the
rest is allocator pages held for reuse. Deleting only *part* of a keyspace is
worse: half-emptied pages cannot be returned at all, and `mem_fragmentation_ratio`
in `INFO` will show it. Both figures are now real rather than derived from RSS, so
the ratio is worth watching.

Redis Cluster behaves the same way in this test — 120 MB resident before and
after a flush — so this is allocator behaviour rather than something specific to
FyroDB.

## Sorted Set Performance

Sorted sets use a score-ordered Vec with a bloom filter for fast membership checks:

- **Ascending score inserts** (leaderboards, time-series): O(1) append — fastest path
- **Random score inserts**: O(log n) position search + O(n) shift
- **Score range queries** (ZRANGEBYSCORE, ZCOUNT): O(log n) binary search
- **Member lookup** (ZSCORE, ZRANK): O(n) linear scan

For best ZADD performance, insert members with ascending scores when possible. The bloom filter skips the O(n) scan for new members that definitely don't exist yet.

## Connection Tuning

Each connection uses:
- 2 KB read buffer (grows on demand for large commands)
- Write buffer shrinks to 32 KB after large responses

For thousands of idle connections, memory per connection is minimal. Under load, buffers grow as needed and shrink back automatically.

## Persistence

- RDB saves every 300 seconds by default (`FYRODB_RDB_INTERVAL`)
- Saves are atomic: temp file → fsync → rename
- BGSAVE runs in a background thread (no fork, no copy-on-write spike)
- On SIGTERM/Ctrl+C, a final save is performed before shutdown

For write-heavy workloads, increase the interval:
```bash
FYRODB_RDB_INTERVAL=600  # save every 10 minutes
```

## Monitoring

Use the INFO command to check memory health:

```
redis-cli -p 8000 INFO
```

Key metrics:
- `used_memory` — actual data allocated
- `used_memory_rss` — OS-level RSS (physical memory)
- `mem_fragmentation_ratio` — RSS / allocated (close to 1.0 is ideal)
- `connected_clients` — active connections
- `total_keys` — live key count

## DB Cache Proxy in Production

### Proxy Workers

Set `FYRODB_PROXY_WORKERS` to the number of physical CPU cores you want dedicated to proxy traffic. The default (num_cpus / 2) is a sensible split between the KV engine and the proxy. Each worker is a mio event loop thread that multiplexes thousands of connections — you rarely need more than 4 even under heavy load.

```bash
FYRODB_PROXY_WORKERS=4   # on an 8-core machine, leave 4 for the KV engine
```

### TTL Tuning

Start conservative and tighten based on your staleness tolerance:

```bash
FYRODB_PROXY_CACHE_TTL_MS=30000     # 30 s — good default
FYRODB_PROXY_CACHE_TTL_MS=5000      # 5 s — for fast-changing tables
FYRODB_PROXY_CACHE_TTL_JITTER=10    # 10% jitter to spread expiry
```

`FYRODB_PROXY_CACHE_TTL_JITTER` spreads cache entry expiry across a ±10% window so a large cohort of entries doesn't expire simultaneously and hammer the database (thundering herd).

### Trust Auth

Set `FYRODB_PROXY_TRUST_AUTH=true` on internal container networks where network-level isolation is already in place. This eliminates the SCRAM round-trip on every new connection, reducing connection setup latency from ~5 ms to under 1 ms.

```bash
FYRODB_PROXY_TRUST_AUTH=true   # safe inside Docker Compose / Kubernetes pod network
```

### Upstream Pool

Cache hits never touch the upstream pool — only cache misses and new connections use it. The default of 4 idle connections per proxy worker is enough for most workloads. Increase only if you see upstream connection wait times in your query logs.

```bash
FYRODB_PROXY_UPSTREAM_POOL=8   # for workloads with sustained high miss rates
```

### Health Checks

The proxy speaks full PostgreSQL wire protocol. Use standard PostgreSQL health tools:

```bash
pg_isready -h fyrodb-host -p 5432
# or from psql
psql -h fyrodb-host -p 5432 -c "SELECT 1"
```

### Cache-Only vs Dual Mode

| Mode | When to use |
| ---- | ----------- |
| `dual` (default) | App connects cold; first query per pattern goes to Postgres, results are cached automatically |
| `cache-only` | App pre-warms the cache at startup; misses return an explicit error — predictable latency, no surprise database calls |

```bash
FYRODB_PROXY_MODE=dual        # default — automatic cache population
FYRODB_PROXY_MODE=cache-only  # app controls what is cached; misses are errors
```

### Recommended Proxy Configuration

#### High-throughput (8+ core server)

```bash
FYRODB_PROXY_WORKERS=4
FYRODB_PROXY_UPSTREAM_POOL=8
FYRODB_PROXY_BLOCKING_POOL=32
FYRODB_PROXY_CACHE_MAX_KEYS=500000
FYRODB_PROXY_CACHE_TTL_MS=60000
FYRODB_PROXY_TRUST_AUTH=true
```

#### Low-latency reads (small dataset, sub-ms response target)

```bash
FYRODB_PROXY_WORKERS=2
FYRODB_PROXY_CACHE_TTL_MS=5000
FYRODB_PROXY_CACHE_TTL_JITTER=5
FYRODB_PROXY_MODE=cache-only
FYRODB_PROXY_TRUST_AUTH=true
```

#### Memory-constrained container

```bash
FYRODB_PROXY_WORKERS=1
FYRODB_PROXY_CACHE_MAX_KEYS=10000
FYRODB_PROXY_UPSTREAM_POOL=2
FYRODB_PROXY_BLOCKING_POOL=4
```
