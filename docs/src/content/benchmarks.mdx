## Native results · November 19, 2026

With 12 workers, FyroDB served **49.75M GET/s** and **44.27M SET/s** over loopback TCP. Calling the engine directly reached **128.74M GET/s** and **82.59M SET/s**. Each KV phase processed ten million operations on five-byte values.

![Median throughput in millions of operations per second for pipelined GET and SET over TCP and in-process](/benchmarks/2026-11-19/throughput.svg)

The TCP server reached **1,096 MiB peak RSS** and averaged **545 MiB**. The embedded benchmark process, which includes the driver and store, peaked at **863 MiB**. These are medians of whole-suite measurements from three fresh runs of revision `021baed` on an Intel Core i5-11400H. The server and Go client shared all six physical cores and twelve hardware threads.

## Performance improvements

Each row compares medians before and after the named change on the same 12-worker workstation. The November 19 chart above shows a separate three-run measurement of the finished build.

| Change | Workload | Before | After | Change in median |
| --- | --- | ---: | ---: | ---: |
| Grow connection buffers on demand | Pipelined TCP GET | 34.17M/s | 48.40M/s | +41.6% |
| Grow connection buffers on demand | Pipelined TCP SET | 33.39M/s | 46.21M/s | +38.4% |
| Grow connection buffers on demand | Peak server RSS | 1,464 MiB | 933 MiB | −36.3% |
| Grow connection buffers on demand | Average server RSS | 564 MiB | 600 MiB | +6.3% |
| Reuse buffers for consecutive large reads | 1 MiB SET, pipeline 8 | 1,869/s | 2,802/s | +49.9% |
| Protect a batch of embedded reads with one guard | Distinct-key GET | 82.81M/s | 132.36M/s | +59.8% |
| Reuse a protected reply across 64 GETs | Same-key GET | 780.73M replies/s | 1,002.67M replies/s | +28.4% |

The TCP suite used two full runs per build. The 1 MiB measurement used stock `redis-benchmark` with 16 clients. The embedded pipeline comparison used five runs per build. In eight runs per build, the same-key optimization’s distinct-key control moved from 146.32M to 145.30M GET/s (−0.7%). [Download per-run samples, including the 64 KiB and 1 MiB payload sweeps](/benchmarks/2026-11-19/improvements.json).

The update also fixes a crash during concurrent hash-table resizing. Batch prefetch and the SET fallback keep the table alive until access finishes. The isolation and restart checks below cover transactions, snapshots, and persisted binary values.

### Repeated-key GET

A separate embedded run issued 64 GETs for the same key per batch, changing keys between batches across 65,536 populated keys. It produced **993.71M logical GET replies/s** across 25,165,824 replies per run. For a non-expiring value in a protected batch, the engine can look it up once and emit a complete RESP reply for every GET. The chart above uses distinct keys.

### Correctness checks

The same source tree passed 836 Rust workspace tests, with three performance probes ignored. All six native end-to-end suites passed. With 12 workers, Lua and MULTI/EXEC each preserved the 64,000 balance with zero inconsistent snapshots, and WATCH accounted for every committed update. Binary values through 1 MiB survived restart.

### Reproduce the native runs

Run from the repository root on a host with twelve logical CPUs. The TCP measurements use the native launcher’s allocator settings and 100 loopback clients. The deep pipeline sends batches of 2,500 requests per connection with a separate reply reader. Each round used a fresh process for each suite. Repeat three times and take the median of each workload.

```bash
cargo build --release --locked --bin fyro_db
FYRODB_BIND=127.0.0.1 FYRODB_WORKERS=12 ./scripts/bench_local.sh -m all -json tcp.json
FYRODB_WORKERS=12 cargo bench --locked --bench without_tcp -- all --json embedded.json
cargo bench --locked --bench pg_cache_bench -- --smoke
```

Save each round under a separate filename to retain its samples. To reproduce the repeated-key run from this checkout, copy `docs/public/benchmarks/2026-11-19/repeated_get.rs` to `examples/repeated_get.rs` and run `cargo run --locked --profile bench --example repeated_get`. ### Why client methods report different rates

The normal suite's KV values are five bytes. Both the Go suite and redis-benchmark use TCP, but their pipeline depths, key distributions, client CPU budgets and response-processing costs differ. A four-thread stock client and a multi-process capacity diagnostic also measure different load-generator budgets. Compare an optimization with the same client and parameters; a gap between different clients is not itself a server speedup or regression.

## Independent standard-client tests

### Retained FyroDB versus Dragonfly: 5 B through 10 KiB

The official, unmodified **redis-benchmark 8.8.3** client ran with 64 connections, four client threads, pipeline 256 and 100,000 fully populated random keys. Each command executes ten million requests through 1 KiB and two million for larger values, with warmups and three measured rounds. Persistence and eviction are disabled for this in-memory comparison. Both servers have the same 3 GiB memory cap and CPU allocation; their exact immutable image IDs and launch flags are archived with the samples.

The FyroDB column is the retained 3d5ef33d50f9 image. Dragonfly is a single server process using the same allocated worker count; this comparison is not against a Redis cluster.



Four client threads can limit or quantize the reported rate. These rates should not be interpreted as the hardware limit. Contention indicators, image IDs, all three samples, sampled peak RSS and container memory are available in the standard-client records. Reused peer samples are explicitly marked in those records.

### Earlier standalone Redis comparison

A separate, earlier campaign tested FyroDB, Dragonfly and standalone Redis with **64-byte values, one million populated keys, pipeline 1/16/64/256 and three rounds**. The campaign included single-core and multicore runs. The FyroDB image was **5823ed9fc45c**, an earlier build, so these are not current-checkpoint results. The multicore Redis configuration used I/O threads; command execution remained single-threaded.


The historical summary recorded medians without ranges.

### Multi-process capacity diagnostic

Six independent processes, each running the unmodified official client without client threads, tested whether a single load-generator process was limiting throughput. Total completed requests were divided by the **slowest reported client duration**. This is a separate aggregate diagnostic, not the score of one redis-benchmark invocation and not the normal Go suite. The same client count, CPU budget, keyspace and pipeline were used for both servers.


### Other benchmark methods

- **Scalar standard-client guard:** pipeline 1, no client threads, 64 connections, one million requests per command; one/six workers and 64 B/1 KiB values. The latest campaign compares the checkpoint with the rejected admission candidate.
- **Independent memtier cross-check:** an earlier 64 B probe used four threads, sixteen clients per thread, pipeline 64, a one-million-key random workload and five-second GET/SET windows. It has one measured attempt per command/build and is a smoke cross-check, not a statistically established current speedup.
- **Direct Rust engine:** `without_tcp` removes sockets and client parsing. Batched APIs may credit equivalent logical operations. Its ops/s and inverse-throughput ns/op are not TCP request/reply rates or measured latency percentiles. Earlier direct and stable campaigns are listed in the downloadable campaign index.
- **Custom RESP and hot-key clients:** used for targeted copying, concurrency, aliasing and capacity diagnostics; they are labeled separately from the standard client.
- **Latency, memory, ANN and proxy modes:** the Go client supplies `lat`, `mem`, `ann`, `vec` and `pgcache` modes. These are supported measurement tools; the archived KV campaign measured throughput separately from ANN recall, open-loop latency and PostgreSQL performance. Historical vector/proxy figures remain historical.
- **Hardware counters:** instruction, cache and locked-access diagnostics investigate mechanisms. They do not establish end-to-end server throughput on their own.


## Algorithms retained in the runtime

The checkpoint retained guarded value access, script/transaction isolation, snapshot pre-images and WATCH invalidation. [Architecture](/docs/architecture) explains the protection layers.

The retained large-payload changes use bounded scatter/gather replies, one guard per unique entry, a stack ownership index for duplicate entries, partial-write copying before guards drop, tiled SET prefetch and conditionally streaming large overwrites. The streaming path fences stores before publishing completion; repeated hashes conservatively select ordinary cached copying. It adds no persistent per-key or per-connection field.



These graphs show all selected metrics for each cohort, including regressions and unchanged cases. The evidence manifest also lists the small-payload acceptance and scaling records; only image-matched samples are credited to the retained runtime.

## Rejected lock-reduction experiment

An outlined handler reused write admission across adjacent small-value SET batches in a deep parser buffer. It retained the existing entry locks, snapshot hooks, replication/AOF routing and command boundaries. It passed correctness checks, but throughput varied materially and several medians were lower. **Both experimental runtime changes were reverted.** Only the regression tests were kept.


The campaign contains **84 timed samples plus eight full Go warmup suites**: normal suites at one/three/six workers, a separate twelve-worker shared-client case, standard P256 cases at 64 B/1 KiB/10 KiB and scalar P1 cases at 64 B/1 KiB. All attempts are retained. A control measured the **identical checkpoint image under both labels** and demonstrated substantial host variation. A/A samples.

A separate hardware diagnostic observed about **0.48% fewer retired locked-access load instructions per SET**. This is neither a mutex-acquisition count nor a throughput improvement. Diagnostic details · acceptance decision · experimental patch.

Earlier counter-striping and broader admission trials were also rejected or superseded. The campaign viewer links all 23 archived summary campaigns and the manifest includes the available trial state records. Earlier native-client/Docker-server priority mismatches are not the current normal-suite reference.

## Safety and regression coverage

The retained source passed **789 workspace tests, zero failures**, with three existing performance probes ignored, plus **14 large-reply tests with the io-uring feature**, Clippy across all targets with io-uring, formatting and diff checks. These counts are a recorded validation snapshot, not a guarantee about future changes.

New regressions cover:

- Deep binary SET pipelines followed by GET, EVAL, WATCH, MULTI/EXEC and NX fallback on one/six workers.
- Incomplete and malformed protocol packets releasing write admission, and resuming a fragmented command.
- SET+EXPIRE boundaries and mixed 257 B, 4 KiB and 10 KiB payloads.
- Nested writer-scope cleanup and preservation of an already-active writer scope.
- Concurrent deep SET/read/SAVE traffic, complete payloads and WATCH aborts after 64/1024-command write pipelines.

The retained release image's isolation stress ran Lua transfers, MULTI/EXEC transfers and WATCH compare-and-set for **15 seconds each, twelve writers and four readers, on one/six workers**. All six cases passed with zero inconsistent snapshots and zero errors. Lua and MULTI transfers preserved the **64,000** total; each WATCH compare-and-set counter matched its expected successful-update count. SAVE/restart covered thirteen data types in two configurations, plus two affinity checks and three queued-large-reply cases. The rejected candidate also passed these checks; correctness alone did not justify retaining it.

Retained source checks · retained-image isolation · candidate-image isolation · restart checks.

A preliminary full-suite reference with a 3 GiB server cap was OOM-killed; it is recorded in the scaling checks rather than silently counted as a successful run. The matched normal suites use 4 GiB for both builds and had zero OOM kills. Scaling checks.

## Reproduce the measurements

Build a local server image, then choose CPUs for your own topology; the example allocation below is specific to this six-core/SMT host. Use a fresh output directory. The runner builds an unchanged static Go client if no client binary is supplied.

```bash
docker build -t fyrodb:local .
python3 scripts/bench_docker_normal.py \
  --server current=fyrodb:local --workers 1,2,3,6 \
  --server-cpus 0,1,2,6,7,8 --client-cpus 3,4,5,9,10,11 \
  --runs 3 --warmups 1 --memory 4g --client-memory 1g \
  --out temp/bench/normal-new
```

Run the shared-client case separately:

```bash
python3 scripts/bench_docker_normal.py \
  --server current=fyrodb:local --workers 12 \
  --server-cpus 0-11 --client-cpus 0-11 --allow-shared-cpus \
  --out temp/bench/shared-new
```

For an independent client against a separately started, disposable server, this command is an example of the P256 workload, not a complete reproduction of all archived preloading and verification steps:

```bash
docker run --rm --network host --cpuset-cpus 3,4,5,9,10,11 \
  --memory 1g --memory-swap 1g redis:8.8.3 \
  redis-benchmark -h 127.0.0.1 -p 8000 --threads 4 \
  -c 64 -P 256 -n 10000000 -r 100000 -d 64 -t set,get --csv
```

Prepopulate every requested random key, verify DBSIZE and sampled values, run warmups, alternate server order and preserve every result before comparing. `-d` changes the value size; do not change value size without preloading that cohort again. For 4 KiB and larger cohorts the archive uses two million requests per command. Pin immutable server/client image IDs for an exact replay; tags can change.

The raw records preserve exact launch commands, keyspace, payloads, sample reuse, host-pressure and memory fields. `task bench-stable` offers the separate native pinned runner, `task memtier` runs the independent load generator, and `cargo bench --bench without_tcp` exercises the engine without TCP. A standard-client score and a batched engine score measure different work.

To regenerate these docs and graphs from the committed evidence:

```bash
cargo test --workspace
cargo test --features io-uring --test large_replies
cargo clippy --workspace --all-targets --features io-uring -- -D warnings
```

The generator verifies evidence hashes, checks the normal-summary medians against the raw equal-priority samples, validates retained-image identities and emits deterministic SVGs, JSON and CSV. The evidence archive includes historical summaries without relabeling them as current results.
